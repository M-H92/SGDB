Introduction

Ce chapitre traitera de la gestion des droits sous PGSQL
Dans PGSQL, cette gestion se fait via les rôles qui peuvent à la fois représenter un utilisateur ou un groupe d'utilisateur.
Nous verrons qu'un rôle peut posséder des "objets" PGSQL représentant aussi bien des tables que des vues, des fonctions, des procédures stockées, ...
Et qu'un rôle peut attribuer des droits sur les objets qu'il possède pour permettre à d'autres droits d'utiliser ces objets
Dans le même ordre d'idée, on pourra aussi faire hériter un rôle d'un autre pour obtenir un droit enfant disposant au minima des droits du parent.

Notez que ce chapitre est certainement le plus spécifique au SGBD (PGSQL) utilisé.
Pour tout ce qui est gestion des droits sur d'autres SGBD, référez-vous à la documentation du dit SGBD

Sur PGSQL, un objet sql correspond à tout "Tout objet créé via la commande CREATE" (doc)
Il y a plus de choses à dire sur les objets PGSQL, mais en ce qui nous concerne pour ce chapitre, cette définition est suffisante.

Gestion des rôles

Comme beaucoup des éléments de PGSQL, les rôles sont disponibles dans une table de rôles accessible avec cette commande : 

 SELECT * FROM pg_roles;

Cette table nous affiche la liste des rôles ainsi que plusieurs informations sur ceux-ci comme par exemple, nom, héritage, privilèges...

Néanmoins, pour créer un rôle, nous éviterons de réaliser un INSERT dans cette table. Nous utiliserons plutôt la commande CREATE 

 CREATE ROLE mon_role;

Après exécution de cette requête, nous pouvons voir "mon_role" ajouté dans la table de rôles.
Pour nous en débarasser, comme les autres objets que nous avons appris à créer, nous pouvons utiliser la commande DROP 

DROP ROLE mon_role;

Si cela n'était pas évident, il est déconseillé de supprimer les rôles présents par défaut dans votre base de données sans être certain de ce que vous faites...

Si vous avez pris le temps de query votre nouveau rôle avant de le DROP, vous avez certainement remarqué qu'il ne dispose d'aucun privilège (rolcreaterole, rolcreatedb, rolcanlogin... à false).
Vous pouvez lui ajouter ces privilèges en ajoutant des attributes à la commande CREATE ROLE comme suit : 

CREATE ROLE mon_role LOGIN;
SELECT * FROM pg_roles 
    WHERE rolname = 'mon_role';

Votre rôle peut maintenant être utilisé pour se connecter (canlogin set à true)
Vous pouvez ajouter une série de ces attributs à la suite pour ajouter autant de privilèges que vous le souhaiter en notant parfois quelques restrictions comme, par exemple, le privilège super user ne pouvant être attribué que si vous êtes vous-même super user
Ci-dessous, une liste des différents attributs avec une courte description de ce qu'ils permettent.
Pour plus de détail, se référer à la doc .

  • LOGIN : dispose d'un shortcut avec la commande "CREATE USER". Permet de se connecter à la db
  • SUPERUSER : ne peut être créé que par un super user. Court-circuite les autres règles
  • CREATEDB : l'utilisateur peut créer une base de données. Il en est alors le propriétaire
  • CREATEROLE : peut créer, modifier et supprimer les rôles non super user.
  • PASSWORD : Ajouter un mot de passe passé en string après l'attribut - CREATE ROLE foo PASSWORD 'mdp'
  • NOINHERIT : Le rôle n'hérite pas des privilèges des autres rôles dont il fait partie (ce qui est le comportement par défaut)
  • BYPASSRLS : Des règles peuvent être appliquées sur les records. Ceci permet d'outrepasser ces règles (RLS => Row-Level Security)
  • CONNECTION LIMIT : Le nombre de connection concurrentes que ce rôle permet de faire. -1 permet de ne pas limiter le rôle

Vous aurez remarqué que l'attribut CREATEROLE permet de modifier un rôle.
Ceci est faisable en remplaçant CREATE par le mot-clé ALTER

Privilèges

Comme cité plus haut, un utilisateur peut créer des objets.
À la création, un objet n'est manipulable que par son créateur et les super users.
Pour modifier ce comportement, nous pouvons attribuer des privilèges.
Ci-dessous, la liste des différents privilèges. Notez que les privilèges applicables dépendent du type d'objet (vue, table, procédure stockée...)

  • SELECT
  • INSERT
  • UPDATE
  • DELETE
  • TRUNCATE
  • REFERENCES
  • TRIGGER
  • CREATE
  • CONNECT
  • TEMPORARY
  • EXECUTE
  • USAGE
  • SET
  • ALTER SYSTEM
  • MAINTAIN

La possibilité de détruire un objet, par contre, n'est disponible que pour le possesseur de l'objet (par défaut, le créateur), les super users ou tout rôle héritant du rôle du possesseur de l'objet.
Il n'est pas possible d'attribuer ce privilège à un autre rôle qui est, par défaut, attribué au créateur de l'objet...
Il est par contre possible d'assigner un nouveau possesseur avec la commande ALTER 

ALTER TABLE table_name OWNER TO new_owner;

Pour ce qui est des autres privilèges, vous pouvez les attribuer à un rôle grâce à la commande GRANT ou les retirer avec la commande REVOKE 

-- Attribuer un privilège
GRANT UPDATE ON table_foo TO jon_doe;
-- Retirer un privilège
REVOKE UPDATE ON table_foo FROM jon_doe;

Deux mots-clefs spéciaux, ALL et PUBLIC permettent d'attribuer tout les privilèges pour l'un et à tout les rôles pour l'autre et s'utilisent respectivement à la place du nom du privilège ou du rôle.

La plupart de ces privilèges sont très explicite (SELECT permet de réaliser des opérations de SELECT sur les tables et colonnes, UPDATE..., DELETE... )
Néanmoins, certains vous semblent peut-être moins évident. Expliquons les :

EXECUTE: permet d'appeler les fonctions et procédures stockées.

USAGE : différent selon les objets.
Pour les langages installés, permet de les utiliser dans les fonctions, procédures stockées,...
Pour les schémas, permet l'utilisation des objets contenu dans le schéma
Pour les séquences, permet l'utilisation explicite des fonctions currval et nextval

SET, ALTER SYSTEM et MAINTAIN permettent des opérations sur lesquelles nous ne nous étendrons pas dans ce cours comme par exemple, les REINDEX, VACUUMING...
Ces opérations sortent du cadre de ce cours.

Mettons en place ce que nous venons de voir en créant un rôle et en lui ajoutant des privilèges sur notre table nageur.
D'abord, vérifions les privilèges actuellement disponibles sur cette table : 

SELECT *
FROM information_schema.role_table_grants 
WHERE table_name='nageur'

Dans la colonne grantee, vous pouvez voir quel rôle dispose d'un privilège. Accessoirement, vous pouvez voir dans la colonne grantor qui a donné ce privilège
La colonne privilege_type permet de savoir lequel des privilèges (parmis la liste plus haut) a été donné au rôle.
Pour l'instant, vous ne devriez voir que votre super user que ce soit en tant que grantee ou grantor.
Il devrait aussi avoir tout les privilèges possibles pour ce type d'objet.

Créons un nouveau rôle et laissons lui la possibilité de
Se connecter
Lire les données de la table nageur 

CREATE ROLE mon_role LOGIN;
GRANT SELECT ON nageur to mon_role;
SELECT *
FROM information_schema.role_table_grants 
WHERE table_name='nageur' 
    AND grantee = 'mon_role';

Il est possible, selon la configuration de votre base de données, qu'il soit nécessaire à votre rôle de disposer d'un mot de passe pour pouvoir se connecter.
Si cela était le cas, ajouter l'attribut PASSWORD lors de la création de celui-ci (cf liste des attributs)

À première vue, cela semble avoir marché.
Essayons de nous connecter et de faire des opérations sur notre base de données...
Nous pouvons effectivement faire des SELECT sur la table nageur.
Mais essayer de modifier les données de celle-ci ou de lire les données d'une autre table nous retourne l'erreur suivante : 

ERROR:  droit refusé pour la table ...
SQL state: 42501

L'erreur est on ne peut plus clair et, au besoin, le code d'erreur retourné correspond à "insufficient_privilege"

Reconnectons nous et supprimons cet utilisateur : 

DROP ROLE mon_role;

Ici aussi, un message d'erreur.
Ce dernier nous indique que des éléments dépendent de notre rôle.
Dans notre cas, cela correspond aux privilèges attribués à celui-ci (comme suggéré dans la partie "hint" du retour d'erreur)
Supprimer ces privilèges permettra de supprimer ce rôle sans autres problèmes

REVOKE ALL ON nageur FROM mon_role;
DROP ROLE mon_role;

Ajoutons à cela qu'un objet doit avoir un propriétaire.
Dans le cas contraire, le rôle ne peut pas être DROP
Une solution à ce problème est d'utiliser les commandes :
REASSIGN OWNED BY mon_role TO autre_role;
DROP OWNED BY mon_role;
DROP ROLE mon_role;

Notez qu'il est possible d'ajouter plusieurs privilèges à la suite dans la même commande ou qu'il est possible de spécifier les colonnes sur lesquelles on souhaite ajouter un droit 

GRANT SELECT, UPDATE, INSERT ON nageur TO mon_role;
GRANT SELECT (nom, equipe_id), UPDATE (equipe_id) ON nageur TO mon_role;

Groupes de rôles

Nous avons vu comment créer des rôles et comment donner des attributs aux rôles.
Cela couvre déjà beaucoup de cas d'utilisations, mais peut vite devenir contraignant quand le nombre de rôles nécessaires augmente.
Pour palier à ce problème, allons utiliser la capacité des rôles à hériter les uns des autres pour construire des "groupes".

La notion de "groupe" de rôle tout comme la notion "d'utilisateur" disposant de rôle n'existe plus dans pgsql depuis les versions 8+
On ne parle plus maintenant que de rôle étant à la fois rôle, utilisateur, groupe...
Gardez ceci en tête quand les termes de groupe ou utilisateur seront utilisés ici comme raccourcis.

Faire hériter un rôle à un autre se fait avec la commande GRANT tout comme pour l'ajout de privilèges.
Regardez plutôt l'exemple ci-dessous : 

CREATE ROLE nageur_lecture_seule;
CREATE ROLE nageur_lecture_seule_logs;
CREATE ROLE nageur_full_access;

GRANT SELECT ON nageur TO nageur_lecture_seule;
GRANT SELECT ON log_nageur TO nageur_lecture_seule_logs;
GRANT SELECT, UPDATE, DELETE ON nageur TO nageur_full_access;

CREATE ROLE jon_doe LOGIN PASSWORD 'lapin';

GRANT nageur_lecture_seule TO jon_doe WITH INHERIT TRUE;
GRANT nageur_lecture_seule_logs TO jon_doe WITH INHERIT TRUE;
GRANT nageur_full_access TO jon_doe WITH INHERIT FALSE;

Ici, nous commençons par créer 3 rôles qui serviront de "groupes" : nageur_lecture_seule, nageur_lecture_seule_logs et nageur_full_access
Ces trois groupes ont pour but de gérer les droits pour les tables nageur et log_nageur. Nous attribuons les privilèges correspondants avec dans les trois lignes suivantes.
On crée maintenant un rôle dont le but sera de créer un utilisateur.
Notez la différence ici entre les rôles de "groupe", fonctionnels et les rôles "d'utilisateur"
Les premiers sont créés sans l'attribut LOGIN.
Effectivement, ces rôles n'ont pas pour but de permettre de se connecter à la base de données directement, mais uniquement de gérer les différents droits d'accès des autres rôles.
Enfin, on fait hériter les droits des rôles de "groupe" à notre rôle "utilisateur".
Ici, la commande GRANT est utilisée pour désigner un rôle attribué à un autre rôle.
Notez que l'on peut faire hériter un rôle de plusieurs autres rôles.
Remarquez qu'un attribut INHERIT est passé à TRUE dans les 2 premiers cas et à FALSE dans le second.
Testons la différence on nous connectant et en manipulant la table nageur

Après avoir fait nos tests, nous remarquons que l'on peut faire nos SELECT sans problèmes sur les tables nageur et log_nageur
Par contre, il nous est impossible de modifier ou supprimer les enregistrement de cette dernière.
Ceci est dû au fait d'avoir spécifié INHERIT FALSE.
Quand cet attribut est spécifié, les privilèges du rôle ne sont pas automatiquement transmis.
Par contre, on peut les utiliser ponctuellement en utilisant la commande SET pour endosser temporairement un de ces rôles 

SET ROLE nageur_full_access;
UPDATE nageur SET equipe_id = null;

L'effet sera effectif jusqu'à la fin de la session de l'utilisateur connecté et peu, grâce à la commande RESET ROLE; être interrompu prématurément.

Un dernier point à relevé sur les rôles utilisés comme "groupe" concerne la suppression de ceux-ci.
Dans le cas précédent, supprimer l'un des rôles hérité par le rôle "utilisateur" (DROP ROLE nageur_lecture_seule;, par exemple) aura pour effet de priver le rôle "utilisateur" des droits strictements hérités du rôle supprimé.
Il n'y a donc pas de suppression en chaîne entrainant la suppression du rôle "utilisateur"
Si le rôle "utilisateur" disposait d'un privilège identique de la part de plusieurs rôles "groupes", il disposera encore de son privilège... Via l'un des autres rôles "groupe".

Security definer

Si vous aviez encore des triggers écrivant des logs lors de la modification de la table nageur, vous avez certainement eu une erreur spécifiant que vous n'aviez pas le droit d'écrire dans cette table de log
Lors de l'appel d'une fonction, procédure stockée,... Il est nécessaire de définir quels rôles sont utilisés pour l'exécution
Par défaut et pour éviter tout accidents, les rôles de l'utilisateur courant sont utilisés.
Néanmoins, ceci est modifiable avec l'attribut SECURITY qui pourra prendre l'une des deux valeurs suivantes :
INVOKER, par défaut, utilise les droits de l'utilisateur "invoquant" la procédure, la fonction...
DEFINER, en revanche, utilise les droits du créateur de l'objet.
Ainsi, on pourra redéfinir notre trigger en spécifiant SECURITY DEFINER pour écrire dans la table de log sans donner le droit d'écriture à l'utilisateur

Exercices

Inscription de patients

Créer une base de données maison_medicale
Créer trois tables: patient, info_personnelle et audits
Créer une procédure stockée : ajout_patient
La table patient contient au moins le nom, prénom ainsi qu'un id numérique
La table info_personnelle contiendra date de naissance, poids, taille, ...
La table audits contiendra des logs pour les écritures, modifications et suppression réalisées sur l'une des deux tables précédentes
La procédure stockée permettra d'insérer un patient ainsi que les informations personelles de celui-ci
Si nécessaire, créer un trigger pour la table d'audit
Créer ensuite un ou plusieurs roles permettant à un utilisateur "plateforme_web" de se connecter et ayant uniquement la possibilité de sélectionner un patient dans la table patient ou d'encoder un patient via la procédure stockée

Prise de rendez-vous

Ajouter une table praticien et une table rendez_vous
Un praticien peut prendre rendez-vous avec un patient pour peu qu'il n'ai pas de rendez-vous à ce moment.
Un rendez-vous dure strictement 30 minutes
Un rendez-vous commence soit à l'heure exacte soit à l'heure et demie
Un rendez-vous concerne 1 patient et 1 praticien à la fois.
Un praticien peut prendre n'importe quel patient en rendez-vous
Créer une vue permettant de reprendre uniquement les disponibilités d'un praticien sans spécifier les rendez-vous déjà prévus (on donne les disponibilités, pas les rendez-vous)
Créer une procédure stockée permettant de créer un rendez-vous entre un praticien et un patient
Créer une fonction permettant de récupérer les prochains rendez-vous pour un utilisateur
Ajuster vos droits pour que l'utilisatuer "plateforme_web" n'ai puisse pas consulter directement la table de rendez-vous ou de praticiens, mais uniquement utiliser les la vue, procédure stockée ou fonction cité plus haut.
Attention, un rendez-vous ne peut pas être créé dans le passé.

Suppression de patients

On souhaite ajouter la possibilité de supprimer des patients ainsi que leurs données personnelles
Pour éviter un éventuel accident, on ajoutera un flag dans la table patient permettant de spécifier que ce dernier est activé ou désactivé
Créer une procédure stockée permettant de désactiver un patient ainsi que de décommander ses rendez-vous à venir.
Mettre à jour les rôles de telle manière que l'utilisatuer "plateforme_web" ne puisse pas supprimer directement les patients mais puisse passer par cette procédure stockée

RGPD

Dans le cadre des lois visant à protéger les données personnelles des utilisateurs, il est demandé aux entreprises de pouvoir justifier de la mise en place de mesures permettant de détruire les informations personnelles d'un utilisateur
Pour se faire, il sera nécessaire de supprimer les informations d'un utilisateur ou d'obfusquer toute information permettant de relier les données à une personne réelle
Créer une procédure stockée capable de réaliser cette opération.
Créer un rôle "securite" capable d'effectuer cette opération pour un utilisateur
N'ajouter que les droits strictement nécessaire à cet utilisateur pour effectuer cette opération grâce à un identifiant qu'il aurait récupéré avec un SELECT sur la table des patients
Accessoirement, créer une fonction permettant au rôle "plateforme_web" de récupérer uniquement les utilisateurs qui ne soient ni supprimés ni obfusqués.
Retirer les droits de consultation directe de la table "patient" au rôle "plateforme_web"
