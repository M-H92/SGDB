Introduction

Dans le cours d'introduciton au SQL, vous avez au l'occasion de manipuler requêtes imbriquées et groupements.
Ceci permettant de récupérer de la donnée de plusieurs tables et d'utiliser des fonctions d'agrégation.
Si ces techniques fonctionnent, elles peuvent ne pas être le plus pertinentes d'un point de vue des performances.
Les fonctions fenêtrées ainsi que les CTE peuvent résoudre ces problèmes.

Base de données test

Ci-dessous, le code permettant de réaliser une base de données de test pour ce chapitre.
Cette base de données représente des articles avec un prix qui sont arrangés en lot dans un espace de stockage.

Fonction fenêtrée

Si nous souhaitons récupérer le total pour chaque article, nous aurions certainement utilisé la fonction d'agrégation 

SUM()

Néanmoins, cette approche nous forcerait à grouper nos lignes de telle manière qu'il serait complexe de récupérer les données de l'article en plus de cette somme.
Rappelons nous : 

SELECT a.nom, id_article, SUM(quantite) FROM lot as l
LEFT JOIN article AS a 
	ON l.id_article = a.id
GROUP BY id_article;

Cette requête résulterait en une erreur. Il est impossible de récupérer le nom de l'article vu que celui-ci n'est pas repris dans la clause "GROUP BY".
Il faudrait donc transformer cette requête de telle sorte : 

SELECT 
	a.nom, 
	id_article, 
	SUM(quantite) 
FROM lot as l
LEFT JOIN article AS a 
	ON l.id_article = a.id
GROUP BY id_article, a.nom;

Mais dans notre contexte, récupérer la somme de tout les articles ne nous intéresse sans doute pas.
Il faudrait sans doute grouper aussi les colonnes par emplacement de lot ainsi que par date.
En bref, la complexité de notre requête va aller croissant.

L'utilisation d'une fonction fenêtrée permettra de réécrire cette requête comme ci-dessous : 

SELECT 
	a.nom, 
	l.*, 
	SUM(quantite) OVER (PARTITION BY id_article)  
FROM lot AS l
LEFT JOIN article AS a 
	ON l.id_article = a.id;

Cette requête n'est pas encombrée des contraintes liées à la clause GROUP BY.
Le résultat est néanmoins différent et je vous invite à comparer les deux résultats sur nos données de test

Dans le premier cas, nous pouvons voir que nous disposont d'une unique ligne par article (vu qu'elles sont groupées sur la colonne article_id)
Dans le deuxième cas, nous avons autant de résultat que de lot.
Néanmoins, la somme, elle, est bien identique dans les deux requêtes.

Nous pouvons voir dans notre requête l'utilisation d'un nouveau mot-clé : 

OVER
.
Ce mot-clé permet d'indiquer sur quelles données appliquer notre fonction et permet de différencier une fonction fenêtrée d'une fonction d'agrégat avec GROUP BY.
Plus loin, le mot clé 
PARTITION BY
permet de grouper les données sur une série de critères comme la clause GROUPE BY
À noter que seul ce premier mot-clé est requis.
Si nous ne créons pas de partitions sur lesquelles exécuter la fonction, elle s'exécutera sur toutes les lignes retournées : 

SELECT 
	a.nom, 
	l.*, 
	SUM(quantite) OVER (PARTITION BY id_article)  
FROM lot AS l
LEFT JOIN article AS a 
	ON l.id_article = a.id;

N'étant pas limité par les contraintes d'un group by, nous pourrions réaliser ce genre de requête : 

SELECT 
	a.nom, 
	l.*, 
	SUM(quantite) OVER () AS total, 
	SUM(quantite) OVER (PARTITION BY id_article) AS total_par_article,
	(SUM(quantite) OVER () - SUM(quantite) OVER (PARTITION BY id_article)) AS difference 
FROM lot AS l
LEFT JOIN article AS a 
	ON l.id_article = a.id;

Nous avons ici plusieurs partitions différentes qui auraient été l'équivalent de plusieurs GROUP BY différents.
Nous pouvons donc comparer des résultats sur plusieurs partitions différentes. Ce qui aurait été plus complexe avec des GROUP BY (plus complexe, pas impossible)

Une autre capacité des fonctions fenêtrées est la possibilité d'ordonner les résultats utilisés pour notre partition.
Comparer donc les résultats des deux requêtes suivantes : 

SELECT a.nom, l.*, SUM(quantite) OVER (PARTITION BY a.id )  FROM lot AS l
LEFT JOIN article AS a 
	ON l.id_article = a.id
WHERE a.id = 1;
			
SELECT 
	a.nom, 
	l.*, 
	SUM(quantite) OVER (PARTITION BY a.id ORDER BY emplacement_x ASC)  
FROM lot AS l
LEFT JOIN article AS a 
	ON l.id_article = a.id
WHERE a.id = 1;

La seconde nous présente le "rollup" des données. Ce qui pourrait être intéressant, dans nos données d'exemple, de voir l'évolution des quantités vendues.

CTE

Les CTE ou Common Table Expression (aussi appelées, dans la documentation PGSQL, "WITH queries") permettent de cibler un portion de notre base de données et de l'utiliser dans nos requêtes
À la différence des window function, ces données n'ont pas forcement de liens avec les lignes récupérées
On pourra plutôt les considérer comme une table temporaire résultant d'une query tout à fait différente.

Prenons cet exemple : 

WITH qtt AS(
	SELECT id_article, SUM(quantite) AS somme FROM lot
	GROUP BY id_article
)
SELECT a.nom, qtt.somme FROM article AS a
LEFT JOIN qtt ON qtt.id_article = a.id;

Les résultats sont les mêmes que notre requête avec GROUP BY ou partition.
Néanmoins, la démarche au niveau de la base de données est différente.
Nous disposons de deux requêtes dont l'une est utilisable dans l'autre.
Ceci permettant de nous libérer des contraintes d'un GROUP BY classique qui force à référencer et grouper toutes les colonnes ou d'une fonction fenêtrée qui utilise les données récupérées par notre requête principale

Un autre aspect des CTE est qu'il permet de réduire la difficulté de requêtes qui peuvent être lourdes ou complexes en séparant une partie de la logique dans un premier résultat... Ou 2, 3,...
Car il est tout à fait possible d'enchainer les CTE les unes avec les autres comme dans cet exemple : 

WITH qtt_1 AS(
	SELECT id_article, SUM(quantite) AS somme FROM lot
	WHERE emplacement_y = 1
	GROUP BY id_article
), qtt_2 AS
(
	SELECT id_article, SUM(quantite) AS somme FROM lot
	WHERE emplacement_y = 2
	GROUP BY id_article
),qtt_3 AS
(
	SELECT id_article, SUM(quantite) AS somme FROM lot
	WHERE emplacement_y = 3
	GROUP BY id_article
),qtt_4 AS
(
	SELECT id_article, SUM(quantite) AS somme FROM lot
	WHERE emplacement_y = 4
	GROUP BY id_article
)
SELECT a.nom, 
	qtt_1.somme AS emplacement_1, 
	qtt_2.somme AS emplacement_2,
	qtt_3.somme AS emplacement_3,
	qtt_4.somme AS emplacement_4 FROM article AS a
LEFT JOIN qtt_1 ON qtt_1.id_article = a.id
LEFT JOIN qtt_2 ON qtt_2.id_article = a.id
LEFT JOIN qtt_3 ON qtt_3.id_article = a.id
LEFT JOIN qtt_4 ON qtt_4.id_article = a.id;

Si le code ci-dessus est compréhensible, il est peu optimisé pour ce qu'il souhaite faire et ne sert qu'à démontrer l'enchainement des CTE.
Gardez en tête que chaque CTE correspond a une requête dans un monde séparé et ne profite pas des autres récupérations de lignes à la différence d'une fonction fenêtrée.

CTE récursive

Un autre point d'intérêt avec les CTE est la possibilité d'utiliser la récursivité avec ce genre de nomenclature : 

WITH RECURSIVE foo(n) AS (
    VALUES (1)
  UNION ALL
    SELECT n+1 FROM foo WHERE n < 100
)
SELECT sum(n) FROM foo;

Analysons ensemble ce code.
Comme dans une CTE, nous avons le mot-clé WITH, le nom de la CTE (foo) et un alias référençant une requête
Par contre, nous avons un élément supplémentaire : le mot-clé RECURSIVE qui va permettre à notre requête de référencer son propre résultat.

Cette requête n'étant pas la plus explicite, analysons celle-ci : 


CREATE TABLE tache(
  id INTEGER PRIMARY KEY,
  id_parent INTEGER,
  description VARCHAR(64),
  temps_requis INTEGER
);

INSERT INTO tache
(id, id_parent, description, temps_requis)
VALUES
(1, null, 'A', 1),
(2, 1, 'B', 2),
(3, 2, 'C', 3),
(4, null, 'L', 4),
(5, 4, 'M', 5),
(6, 5, 'N', 6);

SELECT * FROM tache;

WITH RECURSIVE taches(id, id_parent, description, temps_requis) AS (
  SELECT 
    id, 
  	id_parent, 
	description || '', 
	temps_requis 
  FROM tache WHERE id = 6
  UNION ALL
  SELECT 
    tt.id, 
	tt.id_parent, 
	(t.description || tt.description), 
	tt.temps_requis + t.temps_requis
  FROM taches AS t, tache as tt
  WHERE tt.id = t.id_parent
) SELECT id, temps_requis, description FROM taches;

Ici, nous disposons d'une table de tâche.
Chaque tâche peut avoir une tâche enfant.
Pour réaliser A, je dois réaliser B pour lequel je dois réaliser C.
Si je veux réaliser C, je prendrais un temps de 3h
Pour réaliser B, un temps de 2h inhérent à la tâche B, ainsi que 3h de la tâche C pour un total de 5h
A me demanderais 6h en tout.
Notre CTE récursive va d'abord faire un premier SELECT qui sera utilisé après dans une seconde requête
Les résultats de cette seconde requête sont ajoutés aux résultats de la première avec un UNION
Les résultats de la première sont utilisées dans la seconde pour sommer les temps requis ainsi que pour réaliser la condition du WHERE
Enfin, une fois que cette CTE est réalisée, elle est consommée dans la requête en dehors des parenthèses
