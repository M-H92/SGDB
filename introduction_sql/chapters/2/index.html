Introduction

Nous verrons comment résoudre ce problème en ajoutant une série de mot clés à notre boite à outils SQL

Essayez de réfléchir à une solution avant de continuer votre lecture.

Si nous avions pensé à ce problème avant de créer notre table, nous aurions certainement ajouté une colonne permettant de distinguer de quel chat il s'agit. Par exemple name ou cat
Heureusement pour nous, pas besoin de supprimer notre table et toutes les données enregistrées pour recréer une table avec cette colonne supplémentaire
Effectivement, il est possible de modifier la définition d'une table grâce à la commande 

ALTER
.
Essayez donc ce code : 

ALTER TABLE weight 
ADD cat varchar(32);

Ce code permet d'altérer la table weight pour y ajouter une colonne nommée cat de type varchar

Le type varchar permet de stocker du texte d'un nombre de caractères allant jusqu'au nombre précisé lors de la définition de la colonne. Plus d'info via ce lien

Sélectionnez toutes les informations de la table weight pour vérifier que cela ai bien fonctionné... Et voyez un résultat surprenant...
La colonne cat est remplie de l'information [null].
Rassurez vous, c'est normal ! null signifie simplement qu'il n'y a pas de données.
Nous n'avons effectivement jamais renseigné de nom pour nos enregistrements de poids jusqu'à présent vu que la colonne n'existait pas.

Corrigeons ce problème avec le bout de code suivant :

UPDATE weight
SET cat = 'Monza';

Pour ceux qui ont fait un peu d'anglais, vous comprendrez vite que le mot clé UPDATE permet de modifier les valeurs contenues dans une table.
Le mot clé SET permet de spécifier la colonne ainsi que la valeur à attribuer à celle-ci.
Notez encore la mention Monza écrite entre des '.
Il s'agit du nom de mon chat et est écrit entre apostrophes car il s'agit d'une string.
D'une manière générale, vous croiserez souvent les textes entourés par des ' ou bien "

Sélectionnez à nouveau les informations de la table weight pour voir que chaque enregistrement est maintenant au nom de Monza...
Ça ne nous aide pas beaucoup

WHERE

La commande UPDATE a impacté tout les enregistrements de notre table.
Heureusement, nous disposons d'une solution pour ce problème : un nouveau mot clé WHERE
Ce mot clé va nous permettre de spécifier des critères de récupération de données.
Imaginez un if dans votre cours de programmation que vous utiliseriez sur chaque enregistrement de la table souhaitée.
Selon le résultat de cette condition, les enregistrements sont retournés ou non dans les résultats.
Essayons ces deux requêtes : 

SELECT * FROM weight
WHERE weight <= 5;

SELECT * FROM weight
WHERE weight > 5;

La première nous retourne tout les enregistrements de la table weight pour lesquels les valeurs des pesées sont inférieure ou égales à 5
La seconde nous retourne, au contraire, tout les enregistrements pour lesquels les pesées sont strictement supérieure à 5
Ceci a été possible grâce au mot clé WHERE ainsi qu'aux opérateurs "supérieur à" et "inférieur à" similaire à ceux que vous avez déjà rencontré au cours de C
Et ce mot clé nous arrange bien car il est possible de l'utiliser en combinaison au mot clé UPDATE vu plus tôt.
Ainsi, nous pouvons corriger nos données avec cette requête : 

UPDATE weight
SET
    cat = 'Plume'
WHERE
    weight > 5;

Sélectionnons toutes les données de notre table weight.
Plus moyen de se tromper. Les records disposent chacun d'un nom de chat. Soit Monza, soit Plume.
Si je souhaite uniquement les pesées de l'un de ces deux chats ou de tout autre chat ajouté à ma base de données, je peux maintenant les discriminer selon leurs noms comme ceci : 

SELECT * FROM weight
WHERE cat = 'Monza';

Une rapide lecture des résultats permettra de comprendre que nous n'avons plus que les résultats pour lesquels la colonne 'cat' contient la valeur 'Monza'
Nous retiendrons que le mot clé WHERE permet de mettre des conditions sur nos queries.
Que ce soit sur les SELECT, mais aussi sur les UPDATE
Nous retiendrons que le mot clé WHERE s'utiliser avec des opérateurs similaires à ceux utilisés dans votre cours de C < > =
Ce dernier devrait vous intriguer. Il ne s'agit pas d'une erreur dans ce document, l'opérateur de comparaison pour les égalités est bien = et non ==
Nous n'avons pas, dans ce contexte, de variable à laquelle attribuer une valeur.
Il n'y a donc pas besoin de distinger un opérateur d'égalité ou d'attribution de valeur. Ainsi, nous utiliserons un simple = dans nos conditions WHERE.
Essayons maintenant de récupérer les pesées de 'plume' avec cette requête : 

SELECT * FROM weight
WHERE cat = 'plume';

Étrangement, nous n'obtenons pas de résultats...
Ceci provient du fonctionnement de l'opérateur de comparaison qui réalise une comparaison stricte en respectant la casse.
Les résultats de 'Plume' ne sont donc pas accessible avec un = . Nous aurons besoin de l'opérateur ILIKE 

SELECT * FROM weight
WHERE cat ILIKE 'plume';

Cet opérateur est presque spécifique à postgresql et ne répond pas aux standards SQL.
Dans d'autres SGDB, sql server par exemple, vous disposez de l'opérateur LIKE qui dispose du même comportement.
Pourquoi alors avoir introduit un mot clé ILIKE ?
Pour le distinguer du mot clé LIKE aussi existant en PGSQL...
La différence principale étant principalement une considération de la casse pour LIKE alors qu'ILIKE ne la prend pas en considération.
Mais si LIKE correspond uniquement à un ILIKE qui prend la casse en considération, vous pourriez alors vous demander alors quelle est la différence entre LIKE et = ...
Ce serait légitime, mais uniquement car nous n'avons pas encore exploré toutes les possibilités qu'offrent l'opérateur LIKE.
Ce dernier n'a pas pour but de réaliser une comparaison stricte, mais de réaliser du "pattern matching".
Dans vos cours d'OS, vous avez pu rechercher des fichiers en utilisant un "joker" sous la forme d'une * . Vous n'êtes pas certain de ce que vous voulez récupérer, mais ce n'est pas grave car le joker permet de récupérer "n'importe quoi" à cet endroit.
Vous aurez la possibilité de faire pareil avec LIKE et ILIKE en utilisant le joker % .
Essayons donc : 

-- récupère les données de plume
SELECT * FROM weight
WHERE cat ILIKE '%me';

SELECT * FROM weight
WHERE cat ILIKE 'p%e';

SELECT * FROM weight
WHERE cat ILIKE 'plu%';

SELECT * FROM weight
WHERE cat ILIKE '%l%m%';

-- récupère les données de plume ainsi que de monza
SELECT * FROM weight
WHERE cat ILIKE '%m%';

Identités

Avant de passer aux exercices, prenez le temps de réfléchir à la résolution que nous avons apporté au problème de distinction des enregistrements.
Quand nous n'avions que deux colonnes, une pesée dépendait d'une date.
Un poids n'avait de sens que lié à une date. Il ne s'agissait pas de n'importe quelle pesée. Il s'agissait de la pesée du 1/1/2024, du 12/2/2024, ... (en partant de l'à priori qu'il n'y aurait pas de sens d'avoir plusieurs pesées sauvegardée pour une unique date)
Nous allons définir le lien entre ces deux colonnes comme une dépendance fonctionnelle
Quand nous avons ajouté des pesées d'un autre chat, nous avons rompu ce contrat de dépendance fonctionnelles.
Définir une pesée comme la pesée du 12/2/2024 n'est plus suffisant car nous pourrions avoir deux pesées pour cette date. L'une pour Plume et l'autre pour Monza.
Pour résoudre ce problème, nous avons introduit une 3e colonne et, ainsi, modifié ces dépendances fonctionnelles.
Une pesée est maintenant dépendante d'une date ET d'un chat.
À partir de maintenant, vous devriez systématiquement essayer de déceler ces dépendances fonctionnelles.
Nous reviendrons très vite sur ce concept
